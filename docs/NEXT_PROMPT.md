## 1. 背景と目的

### 現状の問題
既存プロジェクトはバニラJS + HTML + CSS の静的サイトで、以下の状態にあります。

- JS/CSS 合計 **約25,300行**、うち4ファイルが1,800〜2,600行の巨大ファイル
- HTML を**文字列連結で生成**している箇所が4ファイルで **約310箇所**、`innerHTML` 代入が **67箇所**
- 状態がグローバル変数と `HallData.store` で**二重管理**され、`syncToStore`/`syncFromStore` で都度同期
- データが **68MB・全フィールド文字列型**で、数値パース処理が各所に散在
- ページ数10（home/daily/analysis/calendar/island/aim/promotion/tenun/ougi/zombie）

結果として、AIによる小さな修正でも状況把握のために巨大ファイルを読む必要があり、
1件の改修に数千クレジットを消費する状態になっています。

### 目的
**AIが安全かつ低コストに編集できる構造**を持つ機能縮小版を、新規に立ち上げます。
既存サイトは凍結せず動かし続け、新実装は**別ディレクトリで並走**させます（失敗しても損失ゼロ）。

### 第1弾のゴール
「日別データ」ページ1枚が、新しいデータ層の上で実用レベルに動くこと。
これが検証できれば、以降のページ移植は同じ型に沿って機械的に進められます。

## 3. 元データの正確な仕様（調査済み・これが唯一の正）

### 3.1 ファイル構造

```
data/YYYY_MM.json   # 2025_01.json 〜 2026_08.json の20ファイル、計68MB
```

中身は「日付キー → その日の全台レコード配列」のオブジェクトです。

```json
{
  "2026_08_16": [ {レコード}, {レコード}, ... ],
  "2026_08_15": [ ... ]
}
```

- 日付キーの形式は `YYYY_MM_DD`（アンダースコア区切り）
- 1日あたりのレコード数 ≒ **445件**（= ホールの全設置台数。日によって増減あり）
- 総レコード数（全20ファイル）= **229,353件**
- `data/2026_08.json` は15日分で約2.0MB

### 3.2 レコードのフィールド（全11個・全て文字列型）

```json
{
  "機種名": "ネオアイムジャグラーEX",
  "台番号": "881",
  "G数": "4002",
  "差枚": "-1221",
  "BB": "11",
  "RB": "11",
  "ART": "0",
  "合成確率": "1/181.9",
  "BB確率": "1/363.8",
  "RB確率": "1/363.8",
  "ART確率": "1/0.0"
}
```

### 3.3 調査で判明した重要事実（設計の根拠）

**全229,353件をスキャンして検証済みの事実です。信頼して設計に使ってください。**

1. **数値5列（`G数` `差枚` `BB` `RB` `ART`）は、全件が例外なく整数としてパース可能。**
   非数値・空文字・カンマ区切り・`null` は **1件も存在しません**。
2. **`台番号` は全件が非負整数。** 英字や記号を含むものは **1件もありません**。
3. **確率4列（`合成確率` `BB確率` `RB確率` `ART確率`）は完全な導出値であり、保存不要です。**
   実データで検算済み:
   - `合成確率` = `G数 / (BB + RB)` → 4002/(11+11) = 181.9 ✅ 実データと一致
   - `BB確率` = `G数 / BB` → 4002/11 = 363.8 ✅ 実データと一致
   - `RB確率` = `G数 / RB`、`ART確率` = `G数 / ART`
   - 分母が0の場合は元データでは `"1/0.0"` と表現されている（後述の扱いに従う）
4. **機種数は1日あたり約93種類。** 同じ機種名が平均5台前後で繰り返し出現します
   → 機種名を辞書化すると圧縮効果が非常に大きい。

### 3.4 データ形式ごとのサイズ実測（1日445台）

**実測値です。この結果に基づき、下記「列指向形式」を採用してください。**

| 形式 | サイズ | 削減率 |
|---|--:|--:|
| 現行（文字列11列そのまま） | 103,471 bytes | — |
| 数値化＋確率列削除（行指向） | 45,308 bytes | 56%削減 |
| **列指向＋機種名辞書化** | **17,134 bytes** | **83%削減** |

### 4.2 変換スクリプト `next/scripts/build_data.py`

`data/*.json` を読み、以下を `next/public/data/` に出力してください。
**Python3標準ライブラリのみ**で書き、外部依存を追加しないこと。

#### 出力1: `index.json`（全体インデックス・数KB）

AIがこのファイルを丸ごと読んでも数百トークンで収まる粒度にしてください。

```json
{
  "generatedAt": "2026-08-18T00:00:00Z",
  "dates": ["2025_01_01", "...", "2026_08_16"],
  "latestDate": "2026_08_16",
  "months": ["2025_01", "...", "2026_08"],
  "machines": ["ネオアイムジャグラーEX", "..."],
  "unitRange": { "min": 1, "max": 999 }
}
```

#### 出力2: `daily/YYYY_MM_DD.json`（1日分・列指向・約17KB）

```json
{
  "date": "2026_08_16",
  "machines": ["機種A", "機種B", "..."],
  "count": 445,
  "cols": {
    "u":   [881, 882, ...],
    "m":   [0, 0, 1, ...],
    "g":   [4002, 3941, ...],
    "d":   [-1221, -942, ...],
    "bb":  [11, 10, ...],
    "rb":  [11, 17, ...],
    "art": [0, 0, ...]
  }
}
```

- `machines` はその日に出現する機種名の配列（ソート済み）
- `m` は `machines` 配列への**インデックス**
- 全配列は同じ長さ（`count`）で、同一インデックスが同一台を指す
- **確率4列は出力しない**（フロントで導出する。3.3-3 参照）

#### スクリプトの要件

- 冪等（何度実行しても同じ結果）
- 進捗を1行ずつ標準出力に出す（月ごとに `2026_08: 15 dates, 6,673 records` 程度）
- 最後に出力ファイル数と合計サイズのサマリーを表示
- 数値パースは `int()` で行い、**もし失敗したら例外を投げて中断**する
  （3.3 の通り現データでは発生しないが、将来のデータ追加時の壊れ検知として機能させる）
- 実行方法: `cd /home/user/webapp && python3 next/scripts/build_data.py`

### 4.3 型定義 `next/src/types/record.ts`

**このファイルが「AIに読ませる仕様書」の役割を果たします。**
50行程度に収め、コメントで各フィールドの意味と単位を明記してください。

```ts
/** 台1台・1日分のレコード（数値は既にパース済み） */
export interface UnitRecord {
  unit: number;      // 台番号
  machine: string;   // 機種名（表示用に解決済み）
  games: number;     // G数（総回転数）
  diff: number;      // 差枚（プラス=出た、マイナス=負けた）
  bb: number;        // BIG回数
  rb: number;        // REG回数
  art: number;       // ART/AT回数
}
```

- 確率は保存せず、`lib/format.ts` の関数で導出すること
- 派生値（合成確率・機械割など）は `UnitRecord` に持たせず、算出関数として分離
- `as any` / `@ts-ignore` は使用禁止

### 4.4 日別データページの機能範囲（第1弾）

**含めるもの（既存の日別ページから抽出した中核機能）:**

| 機能 | 詳細 |

### 4.5 設計ルール（AI編集しやすさのための最重要事項）

これは「動くこと」より優先される要件です。

1. **1ファイル200行以内。** 超えそうなら必ず分割する。
2. **状態の所有者は1箇所だけ。** `DailyPage.tsx` が状態を持ち、子は props で受け取る。
   グローバル変数・シングルトンストア・二重管理は禁止（既存の失敗を繰り返さない）。
3. **計算ロジックは純関数として `lib/` に置く。**
   React に依存させない（テストしやすく、AIが単独で読める単位にする）。
4. **`innerHTML` / `dangerouslySetInnerHTML` は使用禁止。** すべてJSXで表現する。
5. **CSS は CSS Modules（`*.module.css`）で各コンポーネントに隣接配置。**
   色は必ず `theme.css` の CSS 変数を参照し、コンポーネント内で生の色コードを書かない。
6. **`any` 禁止。** `tsc --noEmit` と `eslint` が警告0で通ること。
7. 各ファイル冒頭に **2〜3行のコメント**で「このファイルの責務」を書く
   （AIが1ファイルだけ読んで役割を把握できるようにする）。

### 4.7 表示ロジックの細部（既存挙動に合わせる）

- **確率の表示形式**: `1/181.9`（小数第1位まで）。
  分母が0のとき（BB=0 など）は `1/0.0` ではなく **`-`** と表示する（改善点）。
- **差枚の表示**: 3桁区切り、プラスには `+` を付ける（例 `+1,234` / `-1,221`）。
- **機械割の算出**（サマリーで使う場合）: `(総払出 - 総投入) / 総投入`。
  元データに投入枚数が無いため、**第1弾では機械割を表示しない**。
  差枚・平均差枚・勝率のみを表示すること（推測値を出さない）。
- **日付表示**: 内部キーは `YYYY_MM_DD` のまま扱い、画面表示は `2026/08/16 (日)` 形式に整形する。
